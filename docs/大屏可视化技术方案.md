# 微前端大屏可视化技术方案

> 版本：v1.0
> 适用工程：`e:\qiankunsub`（qiankun 子应用仓库，Vue 3 + Vite）
> 状态：方案评审稿

---

## 一、架构决策：大屏是"独立子应用"，不是主应用的一个页面

### 1.1 结论

**大屏以独立子应用 `sub-screen` 的形式存在**（代码可以继续放在本仓库 `qiankunsub` 中，也可以拆到 `micro-sub-screen` 独立仓库），主应用只保留一个路由入口 `/screen` 和一个挂载容器。

也就是说：**物理上是独立子应用，逻辑上表现为"主应用的一个全屏页面"**。两者并不冲突：

| 维度 | 主应用内页面 | 独立子应用（推荐） |
| --- | --- | --- |
| 依赖体积 | ECharts、DataV、地图 GeoJSON 全部进主包，主应用首屏变重 | 依赖只在子应用包内，主应用零增量 |
| 部署节奏 | 改大屏要重新发布主应用 | 大屏可独立发布、独立回滚 |
| 渲染隔离 | 图表高频重绘与主应用共用主线程/样式 | 独立运行上下文，样式与 DOM 隔离（qiankun 沙箱） |
| 全屏展示 | 需要与主应用布局（Header/Sidebar）做大量条件判断 | 子应用自管布局，`activeRule` 命中后主应用隐藏框架即可 |
| 独立访问 | 无法单独打开调试 | 可直连 `http://localhost:5174` 独立开发与演示 |
| 扩展性 | 多块大屏（经营/运维/安防）会挤在同一工程 | 可按子应用或子路由横向扩展 |

### 1.2 关键约束（决策成立的前提）

1. 主应用需要**为大屏让位**：`activeRule` 命中 `/screen` 时，主应用隐藏 Header/Sidebar，容器占满视口（见 3.3）。
2. 大屏子应用**不能依赖主应用的全局状态**（Vuex/Pinia 实例、全局样式类），只允许通过 qiankun `props` 通信。
3. 大屏需要**独立鉴权通道**（只读 Token），不能假设用户一定从主应用进入（见 8）。

### 1.3 端口与仓库归属

当前本仓库 `vite.config.js` 已固定端口 **5174** 并开启 `cors` / `origin`，且 `src/main.js` 已导出 qiankun 生命周期，因此：

- **推荐**：直接在本仓库 `qiankunsub` 上迭代为 `sub-screen`，端口沿用 **5174**。
- 若现有 demo 子应用需要保留并行开发，则大屏另起仓库 `micro-sub-screen`，端口分配 **5175**，本文所有 `5174` 替换为 `5175` 即可。

> 下文示例统一使用 `5174`。

## 三、集成方案

```javascript
registerMicroApps([
  {
    name: 'sub-screen',
    entry: '//localhost:5174',
    container: '#subapp-container',
    activeRule: '/screen',
    props: {
      token: () => localStorage.getItem('access_token'),
      getContainerSize: () => ({ width: window.innerWidth, height: window.innerHeight })
    }
  }
])

start({ sandbox: { experimentalStyleIsolation: true } })
```

### 3.2 主应用路由与跳转

- 主应用点击"大屏监控"：`router.push('/screen')`，或 `window.history.pushState(null, '', '/screen')` 后由 qiankun 自动接管。
- **注意路由模式**：主应用若为 `hash` 模式，`activeRule` 必须写成 `'#/screen'`，否则永远不会激活。
- 若大屏需要"不切路由也能预览"（弹窗/新窗口），改用 `loadMicroApp` 手动加载，避免与 `activeRule` 抢占同一容器。



## 五、屏幕适配方案（重点）

### 5.1 方案选型

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `rem` + `flexible` | 元素等比放大，文字清晰 | 字体缩放后易出现小数像素、第三方组件需二次适配 | 备选 |
| 百分比 / `vw` `vh` | 无缩放模糊 | 布局易错位，图表容器高度需大量计算 | 不采用 |
| **`transform: scale`（定尺 1920×1080）** | 设计稿 1:1 还原，开发成本最低，图表随容器等比缩放 | 缩放后需处理鼠标坐标、tooltip 定位、超宽屏留黑边 | **采用** |

### 5.2 实现

```javascript
// src/composables/useScreenScale.js
import { onMounted, onUnmounted, ref } from 'vue'

export function useScreenScale(designWidth = 1920, designHeight = 1080) {
  const scale = ref(1)
  let timer = null

  const calc = () => {
    const ww = window.innerWidth / designWidth
    const wh = window.innerHeight / designHeight
    scale.value = Math.min(ww, wh)
  }

  const onResize = () => {
    clearTimeout(timer)
    timer = setTimeout(calc, 100)
  }

  onMounted(() => {
    calc()
    window.addEventListener('resize', onResize)
  })

  onUnmounted(() => {
    clearTimeout(timer)
    window.removeEventListener('resize', onResize)
  })

  return { scale }
}
```

```html
<!-- views/Index.vue -->
<div class="screen-viewport">
  <div
    class="screen-canvas"
    :style="{ transform: `translate(-50%, -50%) scale(${scale})` }"
  >
    <TopBar />
    <LeftPanel />
    <CenterPanel />
    <RightPanel />
  </div>
</div>
```

```css
.screen-viewport {
  position: absolute;
  inset: 0;
  overflow: hidden;
  background: #030a1a;
}
.screen-canvas {
  position: absolute;
  left: 50%;
  top: 50%;
  width: 1920px;
  height: 1080px;
  transform-origin: center center;
}
```

### 5.3 必须处理的细节

1. **不要用 `position: fixed`**：子应用挂在主应用容器内，`fixed` 会相对视口定位，导致与其他层叠层冲突；用容器 `absolute` + 100% 高度。
2. **等比缩放 + 留黑边**（`Math.min`）优先于分别拉伸（`scaleX/scaleY`），避免圆形、地图变形。
3. **缩放后 ECharts 不需重新 `resize`**：canvas 随 `transform` 缩放即可；但**容器真实尺寸变化**（如面板折叠）仍需 `chart.resize()`。
4. **鼠标坐标偏移**：使用 `transform` 后，`getBoundingClientRect()` 返回的是缩放后尺寸，自定义拖拽/连线组件需要按 `1/scale` 换算坐标。
5. **字体下限**：设计稿中字号建议 ≥ 12px，缩放到 0.6 倍时仍可读。
6. **超宽屏（如 3840×1080）**：`Math.min` 会按高度缩放导致左右大量留白，若业务要求"铺满宽度"，改用 `scaleX` 并接受轻微变形，或提供 `fit: 'contain' | 'cover'` 开关。
7. **DPR 与清晰度**：ECharts 设置 `devicePixelRatio: window.devicePixelRatio`，避免缩放后模糊。

## 六、图表与性能

### 6.1 ECharts 封装（必须 dispose）

```javascript
// src/composables/useEChart.js
import * as echarts from 'echarts'
import { onMounted, onUnmounted, shallowRef } from 'vue'

export function useEChart(elRef) {
  const chart = shallowRef(null)
  let observer = null

  onMounted(() => {
    chart.value = echarts.init(elRef.value, null, { devicePixelRatio: window.devicePixelRatio })
    observer = new ResizeObserver(() => chart.value && chart.value.resize())
    observer.observe(elRef.value)
  })

  onUnmounted(() => {
    observer && observer.disconnect()
    chart.value && chart.value.dispose()
    chart.value = null
  })

  const setOption = (option, notMerge = true) => {
    chart.value && chart.value.setOption(option, notMerge)
  }

  return { chart, setOption }
}
```

### 6.2 性能红线

| 项 | 要求 |
| --- | --- |
| 同屏图表实例 | ≤ 12 个，超出考虑合图或分屏轮播 |
| 数据点 | 单系列 ≤ 5000 点，超出使用 `dataZoom` + `sampling: 'lttb'` |
| 动画 | 首屏加载用动画，之后更新 `animation: false`，避免抖动 |
| 更新频率 | 同一图表 ≤ 1 次/秒，批量合并后 `setOption` |
| 内存 | `unmount` 后 `echarts.getInstanceByDom` 必须为空 |

### 6.3 DataV 使用注意

- 优先使用纯 CSS 实现的边框/装饰，`DataV` 组件仅用于确有必要的动效，减少 DOM 数量。
- DataV 的全局样式在 qiankun 沙箱下可能影响主应用，务必开启 `experimentalStyleIsolation` 或用 `scoped` + 唯一根类名包裹。
- 避免多个 DataV 组件各自跑 `requestAnimationFrame`，同屏装饰动画 ≤ 3 个。

## 七、数据更新策略

### 7.1 轮询（排行榜 / 趋势 / 概览）

```javascript
// src/composables/usePolling.js
import { onMounted, onUnmounted } from 'vue'

export function usePolling(task, interval = 30000) {
  let timer = null
  let running = false

  const tick = async () => {
    if (document.visibilityState !== 'visible' || running) return
    running = true
    try {
      await task()
    } finally {
      running = false
    }
  }

  const start = () => {
    stop()
    timer = setInterval(tick, interval)
  }

  const stop = () => {
    timer && clearInterval(timer)
    timer = null
  }

  onMounted(() => {
    tick()
    start()
  })

  onUnmounted(stop)

  return { start, stop }
}
```

要点：

1. **页面不可见时暂停**（`document.visibilityState`），大屏长时间挂机可降低 60% 以上请求量。
2. **串行执行**，`running` 标记防止慢请求堆积。
3. **可取消**：切换路由/卸载时 `AbortController.abort()`，避免已卸载组件回写状态。
4. **间隔约定**：概览 30s、趋势 60s、排行榜 60s、告警 30s。

### 7.2 WebSocket（实时指标 / 告警）

| 项 | 约定 |
| --- | --- |
| 端点 | `ws://api.example.com/ws/screen?token=xxx` |
| 建立时机 | 子应用 `mount` 后建立，`unmount` 主动 `close(1000)` |
| 心跳 | 客户端每 15s 发 `PING`，30s 无响应判定断线 |
| 重连 | 指数退避 1s/2s/4s/8s，上限 30s，最多 10 次 |
| 降级 | 重连失败 3 次后切回轮询，并在顶部显示"实时连接中断"标识 |
| 消息 | `{ event, data }`，按 `event` 分发，未知事件忽略 |

```json
{ "event": "REAL_TIME_METRIC", "data": { "currentOnline": 4521, "timestamp": 1730964131000 } }
```

**数据一致性**：服务端每条消息带 `timestamp`；客户端丢弃乱序（`timestamp` 小于已渲染值）的数据，避免数字回跳。

### 7.3 异常兜底

- 接口失败：**保留上一次数据**，不白屏；顶部显示数据延迟时长。
- 数字类组件做空值/异常值保护（`null` → `--`，负数不进入进度条）。
- 首屏骨架屏，避免接口慢导致大片空白。

## 八、后端技术方案

### 8.1 接口规范

统一响应结构：

```json
{ "code": 200, "message": "ok", "data": {}, "timestamp": 1730964131000 }
```

| 约定 | 要求 |
| --- | --- |
| 响应时间 | P95 ≤ 200ms，P99 ≤ 500ms |
| 超时 | 客户端 10s，服务端聚合任务 5s 降级返回缓存 |
| 鉴权 | `Authorization: Bearer <screen-token>`，只读权限 |
| 限流 | 按 token + IP 双维度，默认 60 次/分钟 |
| 缓存头 | `Cache-Control: no-store`（数据实时性优先，由服务端缓存兜底） |

```java
// Spring Boot 示例；Node/Go 按等价方式配置
```

### 8.4 缓存与聚合（性能核心）

大屏数据全部是聚合结果，**禁止每次请求实时全表统计**。

```text
Redis Key 设计
screen:overview                TTL 30s   概览四指标
screen:trend:24hours           TTL 60s   24 小时趋势
screen:trend:7days             TTL 5min   7 天趋势
screen:rank:region             TTL 60s    地区排行（ZSET）
screen:alerts:latest           TTL 30s    最新告警列表
screen:map:region              TTL 60s    地图分布
```

刷新策略（二选一，建议 B）：

| 策略 | 说明 | 适用 |
| --- | --- | --- |
| A. 读时缓存 | 请求时 `GET` 缓存，未命中则查询并回填（TTL 30s） | 数据量小、请求稀疏 |
| B. 定时预热 | 定时任务每 10s 计算并写入 Redis，接口只读缓存 | 数据量大、并发高（推荐） |

```text
Cron（每 10s）
1. 增量统计（基于时间窗口，避免全表扫描）
2. 写入 Redis（覆盖式 SET，保留上一版本用于降级）
3. 失败则保留旧值，并打点告警
```

数据库侧要求：

- 统计字段建立索引（如 `created_at`、`status`、`region_code` 组合索引）。
- 避免接口内做多表 `JOIN`；需要多维度聚合时预计算到统计表（`stat_daily` / `stat_hourly`）。
- 数据量达到千万级或需要秒级多维聚合，引入 ClickHouse / Doris 作为报表库，业务库只做写入。
- 分页接口用 `WHERE id < lastId` 游标分页，避免大 `OFFSET`。

### 8.5 WebSocket 服务

- 端点：`ws://api.example.com/ws/screen`，握手时校验 `token`。
- 服务端推送频率与业务一致（如在线人数 5s 一次），**不要推送全量列表**，只推变化量。
- 单实例连接数超过 5k 时，引入 Redis Pub/Sub 做多实例广播。
- 服务端需实现 `PING/PONG` 与连接数监控。

## 九、安全要求

1. **只读大屏 Token**：大屏展示终端使用独立 Token，仅能访问 `/api/screen/**`，有效期建议 7 天，可远程吊销。
2. **敏感数据脱敏**：公开展示屏隐藏手机号、精确金额明细、内部主机名；金额可用"万/亿"单位模糊化。
3. **CORS 白名单**：生产环境禁止 `*`；开发环境允许 `localhost:5173/5174/5175`。
4. **接口幂等与防刷**：概览类接口按 token 限流；异常高频请求直接 429。
5. **不落库明文**：大屏专用 Token 不入日志；WebSocket URL 中避免携带长生命周期凭证，优先用短期票据换取连接。
6. **水印**：公开展示场景加静态水印（项目名 + 时间），降低拍照泄露风险。

## 十二、风险与待确认项

| 风险 / 待确认 | 影响 | 建议 |
| --- | --- | --- |
| 主应用路由模式（history / hash）未知 | `activeRule` 写错导致子应用永不激活 | 先确认主应用路由模式再定 `activeRule` |
| 端口 5174 已被现有子应用占用 | 冲突 | 大屏改用 5175，并同步主应用 `entry` |
| 子应用生产构建资源路径 | 主应用加载 404 | `vite.config.js` 配置 `base` 为子应用部署绝对地址，或运行时注入 publicPath |
| 主应用全局样式污染 | 大屏颜色/字体被覆盖 | 开启 `experimentalStyleIsolation`，大屏根节点使用唯一类名前缀 |
| ECharts 与 qiankun 沙箱 | 个别版本 window 代理异常 | 图表库挂载在子应用内初始化，不使用全局 `echarts` 单例 |
| 多块大屏扩展 | 单子应用内路由膨胀 | 采用 `/screen/ops` 等子路由，必要时拆分为独立子应用 |
| 公开展示屏无人值守 | 断网/接口异常白屏 | 本地缓存上次数据 + 断线提示 + 自动刷新重试 |
